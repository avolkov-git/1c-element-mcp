# Модель языка и проекта: карта для агента

## Три взаимосвязанных представления

Проект «1С:Элемент» нельзя анализировать только как набор XBSL-файлов. Поведение формируется тремя слоями:

1. YAML-метаданные объявляют вид элемента, идентификатор, имя, окружение и специализированные свойства.
2. Одноимённый XBSL-модуль реализует обработчики, вычисления и публичные методы элемента.
3. XBQL-запросы либо хранятся отдельно, либо записываются литералом `Query{...}` внутри XBSL.

Пример пары файлов:

```yaml
ElementKind: CommonModule
Name: ApiApplicationsService
Environment: Server
```

```xbsl
import Applications

method GetApplication(Id: UUID): ApplicationDto
    return Applications.Find(Id)
;
```

Имя файла часто совпадает с `Name`, но полагаться только на это нельзя: окончательную идентичность элемента задают `ElementKind`, `Id`, `Name` и положение в подсистеме.

## XBSL

XBSL регистронезависим в пользовательской русской записи, но исходники поставки широко используют английские ключевые слова и идентификаторы. В одном проекте встречаются `method`, `return`, `if`, `for`, `val`, `var`, `use`, а также русские эквиваленты в документации. Агент должен сохранять стиль редактируемого проекта.

Основные конструкции, которые следует распознавать:

- `import Subsystem` и `import Subsystem::Nested` — доступ к экспортируемым сущностям;
- `method Name(Parameters): ReturnType ... ;` — метод, завершающийся точкой с запятой;
- `val` — неизменяемое локальное значение, `var` — изменяемое;
- `Undefined` — отсутствие значения;
- параметризованные типы вроде `Array<Type>` и `Map<Key, Value>`;
- ссылки на методы `&Module.Method` или `&LocalMethod`, используемые как callbacks;
- блок `use AccessContext.Privileged()` — ограниченная область привилегированного выполнения;
- литералы `Query{...}`, `Version{...}`, длительности (`1m`) и коллекции (`[]`, `{}`);
- аннотации над методами и типами: `@Implementation`, `@InProject`, `@ProjectUpdate`, `@ApplicationSetup` и специализированные платформенные аннотации.

Точная семантика типа, аннотации или метода должна извлекаться поиском по `stdlib` и тематическим страницам. Не следует переносить правила обычного BSL из «1С:Предприятия 8» без проверки: XBSL имеет отдельную систему типов, синтаксис и модель окружений.

## Окружения исполнения

YAML-поле `Environment` и доступность библиотек определяют, где исполняется код. Наиболее очевидное разделение — сервер и клиент. Для формы часть логики связана с интерфейсным компонентом и событиями UI; операции над хранилищем, инфраструктурой и секретами должны оставаться на сервере. При генерации кода агент обязан:

- проверить окружение элемента;
- не вызывать серверный API из недоступного контекста напрямую;
- учитывать сериализуемость DTO на границе HTTP/клиент–сервер;
- искать существующий facade/service-модуль перед добавлением новой сквозной зависимости.

## Прикладные элементы

В поставке встречаются как минимум общие модули, структуры, хранимые структуры, перечисления, каталоги, документы, регистры сведений, HTTP-сервисы, контракты сервисов и типов, интерфейсные компоненты, команды, плановые задания, ключи доступа и события журнала. У каждого `ElementKind` своя YAML-схема и генерируемая платформой поверхность XBSL.

Надёжный алгоритм создания элемента:

1. Найти два-три близких примера того же `ElementKind`.
2. Сверить обязательные поля по официальной документации.
3. Создать новый стабильный UUID, если элемент этого требует.
4. Проверить `Environment`, `VisibilityScope`, `Using`/imports и права.
5. Реализовать XBSL с сигнатурами, соответствующими YAML-обработчикам.
6. Запустить штатный LSP и только затем серверную сборку.

## XBQL

XBQL описывает выборки из прикладной модели, а не произвольной физической схемы СУБД. В запросах встречаются `Select`, `From`, условия, соединения, группировки, виртуальные таблицы и платформенные представления ссылок. Имена сущностей берутся из метаданных проекта. При правке запроса необходимо проверить:

- доступность полей в конкретном типе таблицы;
- возможное значение `Undefined` и тип ссылки;
- объём результата и пагинацию;
- выполнение запроса под текущим `AccessContext`;
- отсутствие N+1-обращений в последующей XBSL-обработке.

## Жизненный цикл проекта

Корневые `Project.yaml`/`Project.xbsl` задают свойства и собирают подсистемы импортами. Аннотированные методы могут участвовать в первоначальной установке и обновлениях. Такие методы должны быть идемпотентны относительно повторного запуска, учитывать `PreviousVersion`/`NewVersion` и не разрушать данные старого релиза.

Для агента особенно важны границы:

- изменение YAML может изменить схему хранения или публичный контракт;
- переименование `Name` не равно безопасному переименованию файла;
- удаление элемента требует анализа ссылок, данных и миграции;
- обновление проекта проверяется не только компиляцией, но и обработчиками `@ProjectUpdate`.
