# Граф проекта и анализ влияния

Версия MCP `0.17.0` строит локальный read-only граф подключённого проекта Element. Граф нужен для вопросов
«от чего зависит элемент?», «что может затронуть это изменение?» и «какие структурные проблемы уже видны до
компиляции?». Он дополняет штатный Language Server, но не заменяет его.

## Модель данных

Граф содержит узлы шести типов:

| Тип | Что представляет |
|---|---|
| `element` | YAML-элемент с именем, видом, ID, подсистемой, environment и visibility |
| `file` | YAML, XBSL или XBQL внутри подключённого корня |
| `subsystem` | Каталог с `Subsystem.yaml` или `Подсистема.yaml` |
| `environment` | Значение `Environment`/`Окружение` из метаданных |
| `visibility` | Значение `VisibilityScope`/`ОбластьВидимости` из метаданных |
| `symbol` | Объявление метода, типа, структуры, перечисления или исключения в XBSL |

Каждое ребро содержит `type`, `confidence`, `resolution`, `semantic_guarantee: false` и `evidence` с путём,
строкой, основанием и исходным значением. Внешние пути и полный текст файлов в граф не попадают.

| Ребро | Уверенность | Основание |
|---|---:|---|
| `metadata_file` | high | YAML-файл самого элемента |
| `companion_file` | high | одноимённый XBSL/XBQL рядом с YAML |
| `belongs_to_subsystem` | high | ближайший manifest подсистемы |
| `environment`, `visibility` | high | верхнеуровневое поле YAML |
| `declares` | high | синтаксически распознанное объявление XBSL |
| `imports_subsystem`, `imports_element` | high | явный `import`/`импорт` |
| `uses_subsystem` | high | явная запись `Using` manifest подсистемы |
| `yaml_id_reference` | high | точное совпадение UUID элемента в YAML |
| `yaml_handler` | high/medium | handler в companion-файле или единственное объявление проекта |
| `yaml_type_reference` | medium | имя известного элемента в поле `Type`/`Тип` |
| `lexical_reference` | medium | полное имя элемента вне строк и комментариев XBSL/XBQL |

`high` означает сильное структурное доказательство, но не результат компилятора. `medium` всегда требует
проверки штатным LSP. Кандидаты `find_unused_project_elements` имеют `low`: отсутствие входящего ребра не
учитывает динамический доступ, соглашения платформы и внешних потребителей.

## Инструменты

`get_element_dependencies` выбирает элемент по точному имени, UUID или metadata path и обходит исходящие,
входящие либо оба направления. Глубина ограничена 1–5, результат — 200 узлами и 500 рёбрами. При одноимённых
элементах возвращается `selection_required` со списком кандидатов.

`get_project_dependency_graph` возвращает страницу element-to-element связей. Можно ограничить её подсистемой и
отдельно включить lexical edges. Structural связи с файлами и dimensions остаются доступны через
`get_element_dependencies`.

`analyze_change_impact` выполняет обратный обход от элемента или списка относительных файлов. В ответе есть
объяснимые пути и минимальная уверенность каждого пути. Без аргументов инструмент пытается взять локальный Git
status; если путь изменения недоступен, он не выдумывает исходную сущность.

`get_changed_elements` принимает до 200 явных относительных путей или читает локальный `git status` в обычном
VS Code/standalone окружении. Команда только читает status, имеет timeout и лимит вывода, не меняет index или
working tree. Modified, added, deleted, renamed и untracked различаются; rename сохраняет `old_path`.

В Element IDE штатный `g5rt.team.status` отдаёт только общий `modified`, но не имена файлов. Поэтому MCP не
запускает второй Git-клиент с credentials IDE. При наличии изменений он возвращает `paths_required`; клиент
должен передать пути текущего diff в `changed_paths`. При `modified: false` возвращается пустой список.

`validate_element_structure` сообщает нечитаемые metadata, повторяющиеся UUID, неоднозначные имена, orphan
XBSL/XBQL, неразрешённые imports, отсутствующие/неоднозначные handlers и циклы. Это структурная проверка, не
компиляция. Для точных ошибок языка после неё нужен `get_project_diagnostics`.

`find_unused_project_elements` возвращает только кандидатов для ручной проверки. Публичные элементы по
умолчанию исключены. Ответ никогда не является разрешением удалить файл.

## Инкрементальность и границы

Снимок определяется относительным путём, размером и `mtime_ns` всех поддерживаемых файлов. При изменении проекта
повторно разбираются только новые или изменённые файлы; удалённые записи кэша выбрасываются. Summary каждого
ответа показывает `cache_hit`, `parsed_files`, `reused_files` и `removed_files`.

Обход использует тот же проверенный корень, что и остальные project tools. Скрытые и служебные каталоги
исключены, directory symlink не обходятся, file symlink не читаются, `..` и абсолютные входные пути запрещены.
Размер отдельного файла ограничен 2 МБ, всего проекта — 50 000 файлов. Ответы имеют отдельные лимиты даже тогда,
когда внутренний снимок больше.

По модели Element файлы внутри специальных каталогов `Resources`/`Ресурсы` являются произвольными ресурсами,
а не вложенными элементами, даже если имеют расширение YAML или XBSL. Граф исключает их из исходников; сам
`Resources.yaml`/`Ресурсы.yaml` остаётся узлом описания ресурсов.

## Рекомендуемый процесс агента

1. Вызвать `get_project_status` и `get_project_overview`.
2. Получить изменения через `get_changed_elements` или явно передать пути.
3. До редактирования вызвать `analyze_change_impact`.
4. Для важного medium-ребра проверить определение и ссылки через LSP.
5. После изменения вызвать `validate_element_structure`, затем `get_project_diagnostics`.

Если граф и LSP расходятся, источником точной семантики считается LSP/компилятор; evidence графа остаётся
полезным объяснением того, почему файл попал в анализ.
