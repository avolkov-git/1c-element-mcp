# Управляемые действия Console

Версия MCP `0.20.0` умеет загрузить сборку проекта, обновить приложение до выбранной сборки, запустить или
остановить приложение. Все операции обращаются к API Панели управления Element `9.2.4-6`.

MCP запрещает запись после установки. С `0.23.0` оператор включает нужные операции в локальном UI, а точные
UUID приложения и проекта берутся из изолированной IDE-сессии вызывающего клиента. Console подтверждает связь
приложения с проектом. Ручные UUID-списки удалены. Агент не может изменить эту политику через MCP tools.
Требуется совместимый плагин с [протоколом IDE-сессий v1](ide-session-plugin-task.md).

## Поддерживаемые операции

| Подготовка | Выполнение | Console API |
|---|---|---|
| `prepare_upload_project_assembly` | `upload_project_assembly` | `POST /api/v2/projects/{project_id}/assemblies` |
| `prepare_update_application` | `update_application` | `POST /api/v2/applications/{application_id}/project/update` |
| `prepare_application_state_change(..., "start")` | `start_application` | `PUT /api/v2/applications/{application_id}/status/start` |
| `prepare_application_state_change(..., "stop")` | `stop_application` | `PUT /api/v2/applications/{application_id}/status/stop` |

`wait_console_task` читает существующую application, deployment instance или group task. Инструмент не создаёт
задачу и не повторяет исходную операцию.

Удаление проекта, приложения, сборки или другого объекта не поддерживается.

## Настройка

Откройте локальную страницу MCP, обычно `http://127.0.0.1:9900/`, и раскройте «Действия агента».

1. Включите «Разрешить».
2. Выберите операции.
3. Для загрузки добавьте один или несколько полных путей к каталогам со сборками.
4. Нажмите «Сохранить разрешения».

MCP проверит операции и существование каталогов. Все записи требуют живую IDE-сессию с подтверждённой связью
`application_id → project_id`. Вызовы без неё, в том числе через `stdio`, запрещены. Переданные в prepare UUID
необязательны; если указаны, они обязаны совпадать с сессией.

Выключение действует сразу и сохраняет выбранные операции и каталоги.
Старый `actions.json` (schema 1) читается с `enabled=false` и `migration_required=true`, даже если раньше был
включён. Оператор проверяет операции и явно включает новую политику. Старые UUID не превращаются в разрешение
на все приложения. Сохранение старых полей UUID через UI API отвергается.

Настройка хранится рядом с основным `config.json` в файле `actions.json`. Аргумент
`--actions-config-path` или переменная `ELEMENT_ACTIONS_CONFIG_PATH` задаёт другой путь. Установщик Windows
использует `C:\ProgramData\1c-element-mcp\config\actions.json`. Файл получает тот же ограниченный ACL, что и
настройки Console. На POSIX MCP выставляет права `0600`.

Пример файла:

```json
{
  "schema_version": 2,
  "target_scope": "current_ide_session",
  "enabled": true,
  "allowed_actions": [
    "upload_project_assembly",
    "update_application",
    "start_application",
    "stop_application"
  ],
  "upload_roots": [
    "C:\\Builds\\Element"
  ],
  "max_upload_bytes": 536870912,
  "approval_ttl_seconds": 300
}
```

Редактируйте файл при остановленном MCP или используйте UI. UI выполняет атомарную запись и проверяет
конфигурацию до включения.

## Подготовка и подтверждение

Каждое изменение состоит из двух tool calls.

1. Агент вызывает `get_managed_actions_status`.
2. Агент вызывает подходящий `prepare_*`.
3. MCP читает текущий объект Console, проверяет разрешённую операцию и IDE-scope, возвращает точную цель, параметры, риски и срок
   действия.
4. Агент показывает результат пользователю и ждёт нового явного подтверждения.
5. После подтверждения агент передаёт одноразовый `approval_token` соответствующему execute tool.

Prepare не вызывает POST или PUT. Токен связан с названием операции, целью, параметрами, текущим состоянием и
отпечатком политики и ID сессии. По умолчанию он действует пять минут, но не переживает отзыв или истечение
IDE-сессии. MCP хранит только SHA-256 токена в памяти процесса. Перезапуск MCP аннулирует все подготовленные
операции. Токен одной сессии невозможно выполнить из другой, даже для того же приложения.

Сервер расходует токен до внешнего запроса. Ошибка, смена состояния или неоднозначный сетевой результат не дают
права повторить запись. Для новой попытки пользователь начинает с нового prepare и снова подтверждает цель.

Текущий HTTP-сервер работает в stateless JSON response режиме. Такой режим не гарантирует обратный канал MCP
elicitation во всех клиентах. Поэтому `0.20.0` использует переносимый prepare/execute workflow. Серверная часть
сама обеспечивает разрешённые операции, IDE-scope, привязку токена, срок действия, одноразовость, precondition и отсутствие повторов.
Правило о новом подтверждении выполняет MCP-клиент по server instructions. Клиенты с собственным подтверждением
tool calls добавляют ещё один уровень контроля.

## Загрузка сборки

`prepare_upload_project_assembly` принимает локальный `file_path`, необязательный `project_id` и необязательный
`expected_configuration_id`.

MCP проверяет следующее:

- `project_id` соответствует текущей IDE-сессии и существует в Console;
- путь находится внутри одного из `upload_roots`;
- файл обычный, не symlink, имеет допустимый размер и корректный ZIP-формат;
- в корне ZIP находится один `Project.yaml`, `Проект.yaml` или `V8Assembly.yaml`;
- `Id` или `Ид` внутри YAML имеет формат UUID и совпадает с `expected_configuration_id`, если он задан;
- размер и SHA-256 не изменились между prepare и execute, включая время чтения файла.

UUID проекта Console и `Id` конфигурации внутри архива обозначают разные сущности. MCP требует точный Console
`project_id` для адреса операции. `expected_configuration_id` защищает выбранный архив от подмены другим
проектом.

MCP отправляет содержимое ZIP как `application/octet-stream`. Он не передаёт путь удалённому серверу.

## Обновление приложения

`prepare_update_application` принимает точную строку `assembly_version` и необязательные `application_id`, `project_id`. MCP
читает приложение и сборку через безопасные GET tools. Перед POST он повторно читает приложение и сравнивает
текущий источник, версию, статус и активную задачу с подготовленным состоянием.

Тело запроса формируется сервером:

```json
{
  "source": {
    "type": "repository",
    "project-id": "<project UUID>",
    "assembly-version": "<exact version>"
  }
}
```

Агент не может передать произвольный JSON или URL.

## Запуск и остановка

`prepare_application_state_change` читает карточку и статус приложения. Execute tool повторно сверяет статус и
ID текущей задачи. При изменении любого значения MCP возвращает `precondition_failed` без PUT.

Остановка помечена в MCP как destructive action, потому что пользователи могут потерять доступ к приложению.
Запуск остаётся внешней необратимой записью, но не помечается как удаление данных.

## Задачи и неоднозначный результат

Console часто возвращает `current-task`. Execute tool сообщает `task_id`, но не называет операцию завершённой.
Передайте ID в `wait_console_task`. Тайм-аут ограничен 120 секундами, интервал растёт до 5 секунд. При тайм-ауте
инструмент возвращает последнее состояние задачи.

MCP не повторяет POST или PUT после `401`, `502`, `503`, `504`, разрыва соединения или тайм-аута. Для сетевых
ошибок без достоверного ответа он возвращает `outcome_unknown`, `retry_allowed: false` и список read-only tools
для сверки фактического состояния. Сначала проверьте сборки, приложение, статус и задачи. Новый запрос допустим
только после этой сверки, нового prepare и нового подтверждения.

## Audit log

Каждый prepare, расход токена, отказ и итог записываются отдельным JSON-файлом:

```text
<data_path>/audit/managed-actions/
```

Запись содержит UTC-время, `approval_id`, действие, точную цель, outcome, HTTP status и task ID. MCP удаляет из
текста bearer, authorization, password, secret и token. Сам `approval_token`, Console credentials и тело сборки
в audit не попадают.

Файл `execute_started` создаётся после расхода токена и до сетевой записи. Если процесс завершится во время
запроса, этот факт останется для последующей сверки.

## Проверка на тестовом приложении

Проводите первый настоящий тест на отдельном приложении и проекте.

1. Подключите совместимый плагин и убедитесь, что `get_current_application` возвращает приложение этого окна IDE.
2. Разрешите одну операцию в UI; проверьте `workspace_scope` в `get_managed_actions_status`.
3. Выполните prepare и проверьте имя, UUID, сборку, текущее состояние и риски.
4. Подтвердите выполнение.
5. Дождитесь task через `wait_console_task` и проверьте состояние read-only tool.
6. Откройте audit log и убедитесь, что в нём нет credentials и approval token.
7. Повторите тот же execute token. MCP должен отклонить его без внешнего запроса.
8. Выключите «Действия агента» в UI.

CI проверяет API-контракты и отрицательные сценарии с mock Console. Настоящий smoke-test на Windows остаётся
операторским шагом, потому что он меняет опубликованное приложение.
