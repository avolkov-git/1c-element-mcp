# Задание: изолированные IDE-сессии для 1C Element MCP

## Результат

Реализовать в Codex Element plugin подключение к протоколу IDE-сессий v1 из MCP **0.23.0**.
Пользователь больше не вводит UUID разрешённых проектов и приложений в настройках MCP.
Управляемые действия доступны только для приложения текущего окна Element IDE и связанного с ним проекта.
Два окна IDE, подключённые к одному MCP на порту 9900, не должны заменять контекст друг друга.

Изменять код плагина, его тесты и документацию. Серверная часть уже реализована в репозитории
`1c-element-mcp`; не создавать обход ограничений на стороне агента или альтернативный глобальный handoff.
Наличие версии в исходниках не означает, что MCP уже выпущен или установлен на Windows: перед интеграцией
проверить `/api/status` и доступность нового endpoint. Выпуск и развёртывание согласовать отдельно.

## Почему нельзя просто убрать UUID-списки

В старом плагине `ElementMcpIdeBridgeService` отправляет общий POST `/api/integrations/element-console`.
До 0.23.0 последний handoff заменял контекст всех клиентов. Теперь MCP связывает запрос с неизменяемой
IDE-сессией через отдельный HTTP-заголовок. Сервер проверяет связь приложения и проекта через Console.

Это не определение приложения по папке: источники ID — штатные `1C.projectId` и `1C.applicationId`.
`Project.yaml.Id`, имя репозитория, имя приложения и результаты поиска не заменяют эти значения.
Если официальных ID нет, автоматический доступ к записям не предоставлять.

## Точки изменения в плагине

На исследованной ветке `feature/1.0.5-rc1-browser-viewer`:

- `src/elementMcpIdeBridgeService.ts`: вместо общего handoff — менеджер сессии конкретного окна IDE.
  Сейчас heartbeat пропускается при неизменном fingerprint; это поведение для renew убрать.
- `src/extension.ts`: связать lifecycle менеджера сессии с lifecycle runtime и workspace.
- `src/codexRuntimeController.ts`: установить session-specific MCP configuration до initialize runtime;
  обработать обе ветки запуска (`normal` и `minimal`), restart, retry, reconnect и dispose.
- `src/codexIntegrationsService.ts`: не позволять UI сохранения MCP-конфигурации стирать временную привязку
  или создавать второе unbound-подключение того же сервера.
- `src/browserRuntimeService.ts`: пример существующего process-local `-c mcp_servers...` override.
  Сохранить browser overrides; новый механизм не должен их заменять.

Проверить актуальные имена и интерфейсы перед изменениями: ветка могла продвинуться.
В исследованном `bin/runtime-manifest.json` указан Codex runtime 0.154.0.
Ключи `http_headers`/`env_http_headers` присутствуют в bundled binary, но это не заменяет проверку фактической
доставки заголовка при запуске app-server на целевой ОС.

## Архитектура и границы

Один владелец сессии на окно IDE / extension host с одним workspace-контекстом.
Все Codex-чаты этого окна могут использовать одну сессию, пока идентичность workspace не меняется.
Не делать менеджер singleton между окнами и не хранить session token в общем профиле.

Сессия включает:

- адрес Console и её credentials;
- точные `project_id`, `application_id`;
- список локальных `workspace_folders`;
- необязательную безопасную сводку `g5rt.team.status`.

Сервер проверяет доступ к Console и связь приложения с проектом. Если локальных Element-проектов несколько,
их выбор для чтения остаётся явным среди кандидатов внутри переданных folders; он не меняет цель Console.
Если кандидатов нет, чтение проекта сообщит об этом. Папка сама по себе не доказывает связь с приложением.

Токены имеют разные назначения:

| Значение | Где использовать |
|---|---|
| `mcp_token` | Только HTTP-заголовок MCP transport на `/mcp` |
| `control_token` | Только bridge-запросы renew/revoke |
| `X-Element-MCP-Token` | CSRF-защита локальных служебных endpoint, как в текущем плагине |
| `approval_token` | Одноразовое подтверждение конкретной операции; выдаёт prepare tool |

`control_token` и Console credentials не передавать runtime или модели.
Ни один секрет не помещать в prompt, developer instructions, tool arguments, URL/query, telemetry,
exception dumps, логи, Settings UI или постоянный `config.toml`.
`mcp_token` разрешено передать только приватному окружению процесса runtime, если используется
`env_http_headers`. Это capability для конкретной IDE-сессии, не Console credential.
Не наследовать его shell/tool-дочерним процессам, если runtime позволяет явно исключить переменную из их
окружения; ограничения такого исключения зафиксировать. Не заявлять защиты от агента с произвольным
локальным выполнением или от администратора ОС.

Протокол доверяет локальному bridge с теми же правами пользователя. Это защита от смешения окон и
неверной цели операции, а не многопользовательская OS-аутентификация. Удалённый MCP без отдельной
аутентификации не поддерживается. Сохранить loopback-only проверку URL, ограничения ответов и тайм-ауты.

## HTTP-контракт MCP 0.23.0

### 1. Создание

Получить локальную страницу `GET /`, извлечь meta `element-mcp-token` существующим способом.

`POST /api/integrations/ide-sessions`

Заголовки: `Content-Type: application/json`, корректный `Content-Length`,
`X-Element-MCP-Token: <csrf>`.

Пример тела (ID и пути здесь иллюстративны; отправлять реальные штатные значения):

```json
{
  "protocol_version": 1,
  "server": "https://element.example/console",
  "client_id": "<из 1C.clientId>",
  "client_secret": "<из 1C.clientSecret>",
  "project_id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
  "application_id": "cccccccc-cccc-cccc-cccc-cccccccccccc",
  "workspace_folders": ["C:\\Element\\workspace"],
  "git_status": {"branchName": "master", "modified": false}
}
```

`protocol_version` — целое число 1; оба ID обязательны и должны быть UUID.
`workspace_folders` — непустой список существующих локальных каталогов, доступных процессу MCP,
не URI браузера. Существующая серверная граница — не более 16 folders.
Остальные допустимые поля: `access_token` (альтернативная штатная авторизация вместо client credentials),
`space_id`, `verify_tls`, `ca_bundle`. Не отключать проверку TLS автоматически.
Неизвестные поля отклоняются. Размер JSON ограничен 64 KiB.

Успех — **201**, `Cache-Control: no-store`:

```json
{
  "protocol_version": 1,
  "status": "ready",
  "session_id": "<uuid>",
  "project_id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
  "application_id": "cccccccc-cccc-cccc-cccc-cccccccccccc",
  "workspace_folders": ["C:\\Element\\workspace"],
  "expires_in_seconds": 180,
  "mcp_header": "X-Element-IDE-Session",
  "mcp_token": "<opaque>",
  "control_header": "X-Element-IDE-Control",
  "control_token": "<different-opaque>",
  "lease_seconds": 180,
  "renew_after_seconds": 60
}
```

`expires_in_seconds` может быть меньше 180; это остаток, не абсолютное время.
После ответа проверить версию, обязательные поля, UUID и ожидаемые имена заголовков.
Не доверять произвольным именам headers из неожиданного ответа.
Не логировать полное тело ответа. Отказ создания не заменяет другие живые сессии.
Сервер допускает максимум 32 живые сессии.

### 2. MCP transport

На **каждый** HTTP-запрос соответствующего MCP-клиента, включая initialize, tools/list и tools/call:

```text
X-Element-IDE-Session: <mcp_token>
```

Токен не передаётся аргументом инструмента и не равен стандартному `Mcp-Session-Id`.
Сервер сейчас использует stateless Streamable HTTP; маршрутизация проверяется на каждом запросе.
Повторяющийся, неизвестный или просроченный заголовок даёт **401**:

```json
{"status": "ide_session_required", "message": "<причина>"}
```

При отсутствии заголовка доступны независимые unbound read-only возможности, но управляемая запись
запрещена. Плагину нельзя убирать заголовок как «восстановление» после ошибки.

Предпочтительное подключение — временный override того же MCP server name в конкретном runtime:

```toml
[mcp_servers.<существующее-имя>]
url = "http://127.0.0.1:9900/mcp"
env_http_headers = { "X-Element-IDE-Session" = "ELEMENT_IDE_MCP_SESSION_TOKEN" }
```

Это **образец результирующей process-local конфигурации**, не инструкция записать файл.
Значение переменной задаётся только в `env` запускаемого runtime. Сам секрет не помещать в `-c`/command line.
Не мутировать `process.env` extension host, общий профиль или настройки другого окна.
Имена, quoting TOML, слияние таблиц, видимость env и refresh MCP клиента проверить тестом bundled runtime.
Не дублировать одно подключение под двумя именами. Не считать его автоматически доверенным для записей.

Если штатный runtime не позволяет безопасный per-process header override, остановиться с отчётом и
предложением изменения интеграции. Не заменять его передачей token модели, общим глобальным конфигом,
прокси «последнее активное окно» или неподтверждённым ID из чата.

### 3. Продление

`POST /api/integrations/ide-sessions/<session_id>`

Заголовки: JSON, CSRF и `X-Element-IDE-Control: <control_token>`.
Тело `{}` либо `{"git_status": <безопасная сводка>}`.

Успех **200**: `status`, `session_id`, ID, folders, `expires_in_seconds`,
`lease_seconds`, `renew_after_seconds`; новые токены не выдаются.
Отправлять heartbeat каждые 60 секунд **даже при неизменном fingerprint**. При кратковременном сбое —
ограниченный retry/backoff внутри оставшегося срока, без параллельных renew.
Получение успешного MCP tool result не продлевает сессию.

Нельзя менять credentials, IDs, folders или адрес Console через renew. Для изменения нужна новая сессия.
Просроченную сессию восстановить нельзя.

### 4. Отзыв

`DELETE /api/integrations/ide-sessions/<session_id>`, CSRF и управляющий заголовок; тело не требуется.

Успех **200**: `{"status":"revoked","session_id":"..."}`.
Сервер аннулирует approvals, закрывает отдельный LSP и удаляет сессию.
Повторный DELETE или запрос к уже истёкшей сессии вернёт **401**, а не 200.
Токен MCP не подходит для renew/revoke, управляющий токен не подходит для `/mcp`.
При закрытии IDE отзыв — best effort; heartbeat TTL ограничивает оставшееся время.

Уже отправленный в Console write отменить отзывом нельзя. Серверный revoke ждёт завершения текущей
защищённой отправки. Поэтому после тайм-аута revoke или execute нельзя утверждать, что операция отменена:
нужна read-only сверка, без автоматического повтора.

### 5. Ошибки

- **400** — неверные поля/версия/UUID/workspace, неподтверждённая связь приложения с проектом,
  попытка изменить immutable-контекст, лимит сессий. Показывать безопасное объяснение.
- **401** на session-control — отсутствующий/неверный управляющий токен, неизвестная или истёкшая сессия.
  Ошибка Console при создании также может вернуть 401.
- **403** — локальная CSRF/host-защита либо запрет Console. Обновить CSRF при смене процесса; не зацикливать.
- **413** — отсутствующий/некорректный Content-Length или превышен предел размера.
- **502** — ошибка проверки Console, если её HTTP-статус не 401/403.
- **426** старого `/api/integrations/element-console` — старый handoff больше не поддерживается.
- **404** нового endpoint — несовместимый/старый MCP. Предложить обновить MCP, не переходить на общий handoff.

Редкая гонка expiry во время renew может дать 400 `status=invalid`; для неё также создать новую сессию,
не менять identity существующей. Не определять поведение по русской подстроке сообщения.
Все non-2xx должны блокировать объявление bridge готовым; auth/expiry нельзя лечить удалением session header.

#### Уточнённая диагностика регистрации

Версия 0.23.1 добавляет поле `code` к отказам проверки Console.
Протокол остаётся v1; в 0.23.0 этого поля ещё нет. Клиент должен поддерживать оба формата.

| `code` | HTTP ответа MCP | Причина |
| --- | --- | --- |
| `console_authentication_failed` | 401, 403 или 502 | Ошибка первичной проверки авторизации через список пространств |
| `console_application_failed` | 401, 403 или 502 | Не удалось прочитать и проверить точную карточку приложения |
| `application_project_missing` | 400 | В карточке нет ID проекта в `project.id` или `source.image-id` |
| `application_project_invalid` | 400 | ID проекта из карточки не является UUID |
| `application_project_mismatch` | 400 | UUID проекта приложения отличается от штатного `1C.projectId` |

Поле `http_status` содержит исходный HTTP-статус Console либо `null`, если HTTP-статуса нет.
Например, HTTP 404 от Console возвращается как HTTP 502 от MCP, с `code=console_application_failed`
и `http_status=404`. Это отличается от HTTP 404 отсутствующего endpoint регистрации.
Транспортная ошибка, некорректный DTO или несоответствие ID самой карточки также отклоняют регистрацию;
они не превращаются в несовпадение проектов.

Ответ и журнал MCP содержат локально сформулированное объяснение без исходного тела Console,
credentials и локальных путей. Клиенту следует сопоставлять известные `code` с собственными русскими
сообщениями и показывать общий отказ для неизвестных значений, а не выводить произвольное тело ответа.
Диагностические ответы запрещено кешировать (`Cache-Control: no-store`).

IDE-контекст разрешается до чтения любых общих источников. Повреждённый `console.json`, настройки другой
IDE или переменные окружения не участвуют в выборе соединения сессии. Некорректный IDE-контекст
отклоняется без fallback на общие credentials; уже открытые сессии при отказе не заменяются.

## Lifecycle

Рекомендуемые состояния: `disconnected → connecting → ready → renewing`, затем `expired/revoking/error`.
Использовать generation/epoch: запоздалый ответ не должен активировать старую сессию после смены workspace.
Если create завершился после отмены, отозвать выданную сессию, не подключая её к runtime.

При смене `1C.server`, credentials, `1C.projectId`, `1C.applicationId`, `workspaceFolders`, MCP URL,
или TLS-параметров:

1. Заблокировать новые операции старого MCP-клиента и убрать pending approvals из UI.
2. Отключить старое transport-подключение и отправить revoke старой сессии.
3. Перечитать штатный контекст; создать новую сессию.
4. Установить новый override и восстановить MCP-подключение штатным способом.
5. Проверить `get_managed_actions_status.workspace_scope` и `get_current_application` нового клиента.
   Только после совпадения ожидаемых ID объявить подключение готовым.

При необходимости перезапуска всего app-server сохранить чаты обычным существующим способом.
Не переносить active turn, ожидающий execute, автоматически на новую цель. Повторный prepare и новое
пользовательское подтверждение обязательны.

Для рестарта MCP: старые токены неизвестны, CSRF тоже меняется. Перечитать страницу, создать новую сессию,
пересоздать MCP-клиент и аннулировать approvals. Для restart runtime при той же живой сессии можно сохранить
сессию в bridge-памяти, но headers должны заново попасть в обе ветки запуска.
При смене endpoint не отправлять секреты старой сессии новому адресу.

## UX и совместимость

Показывать состояние «Приложение текущего workspace подключено» только после проверки scope.
При отсутствии ID — «Element IDE не передала текущее приложение. Управляемые действия недоступны».
При старом MCP/плагине — явное требование обновления, без бесконечного spinner.
Обычный VS Code без штатного Element-контекста не получает автоматических прав по папке.
Независимую документацию и read-only режим можно сохранить с явным статусом отсутствия workspace-привязки.
После expiry не подменять сессионный клиент таким read-only подключением незаметно.

В MCP сохранены master switch, выбор четырёх действий, upload roots, проверка архива и состояние объекта,
prepare/execute с новым подтверждением пользователя, audit и запрет повторных POST/PUT.
Политика schema 1 после обновления отключена до явного сохранения оператором в UI schema 2.
Плагин не включает её сам. Поля UUID-allowlist не отправлять. `get_managed_actions_status` содержит
`workspace_scope`, `can_prepare`, `migration_required`; `workspace_scope=ready` само по себе не означает,
что оператор разрешил записи.

## Обязательные тесты

1. Два окна с разными app/project/root подключены к одному MCP; их tool calls и read-only defaults не смешиваются.
2. Два окна одного приложения всё равно имеют разные сессии; approval окна A не работает из B.
3. В normal/minimal runtime startup, retry, reconnect, profile switch и runtime restart заголовок сохраняется.
4. Session token реально доходит через bundled app-server до initialize и tools/call, а не только до mock bridge.
5. Неизменный fingerprint не подавляет heartbeat; renew продлевает lease, но не меняет identity.
6. Смена workspace во время create/renew/prepare: late responses игнорируются, старый token не используется,
   старое подтверждение не выполняется автоматически.
7. Expiry, revoke, crash IDE, restart MCP, отказ Console, отсутствующий application ID,
   несовпадающая связь project/app и недоступный workspace приводят к отказу без fallback.
8. Подстановка UUID другого приложения в prepare отвергается; правильный ID можно вообще не передавать.
9. Неизвестный/повторяющийся header и смешение control/MCP tokens отвергаются.
10. Секреты отсутствуют в логах, prompt, tool arguments, command line, общем `config.toml`,
    сохранённом workspace state и UI. Проверить stdout/stderr диагностические пути и красное отображение ошибок.
11. Старый MCP (404), старый handoff (426), policy migration и выключенные actions объясняются пользователю.
12. Browser MCP, другие пользовательские MCP, вход в аккаунт и восстановление существующих чатов не сломаны.

Тесты MCP уже находятся в `tests/test_ide_sessions.py`, `tests/test_actions.py`, `tests/test_ui.py`.
Использовать их как проверяемый контракт, а не менять сервер, чтобы скрыть дефект плагина.
Первый настоящий write-smoke провести на отдельном тестовом приложении после согласия пользователя:
prepare → показать точную цель → отдельное подтверждение → execute → read-only сверка результата.

## Критерии сдачи

- Код плагина, unit/integration tests, инструкция обновления и release notes готовы.
- Реальная совместная проверка MCP 0.23.0 + bundled runtime на Windows/Element выполнена с двумя IDE-окнами.
- Приведены проверенные версии и результаты сценариев; секретов в артефактах нет.
- Нельзя заявлять готовность, если проверен только POST handoff, но не per-client MCP transport.
- Если Windows, штатные IDs или механизм headers недоступны, явно перечислить непроверенное и блокеры.
  Не подменять это рабочими заглушками или доступом ко всем приложениям.
- Не выпускать/не устанавливать обновления и не менять опубликованные приложения без отдельного разрешения.
